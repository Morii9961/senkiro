## 0. 一页摘要

**一句话定位：** 一个集「全日本铁路地图 / 深度换乘案内 / 票价与票券研究 / 乘坐足迹 / 数字车票收藏」于一体的跨平台铁路探索与旅行记录产品。

**产品不是单纯重造一个乗換案内。** 它把同一套铁路数据串联到完整旅程：**探索铁路 → 规划路线 → 理解票价和通票 → 实际乘坐 → 点亮铁路网络 → 收藏车票与照片**。

**目标平台：** Web、iOS、Android。**目标受众：** 日本自由行旅客、铁路爱好者、乘车收集者（乗りつぶし）、旅行摄影爱好者，以及需要高级换乘比较的用户。

**最关键的差异化：** 对每条线路建立相互关联的车站、运营公司、直通运营、车种、票价规则、通票覆盖、历史与个人乘坐记录，而非把这些信息拆成互不相干的页面。

**首个推荐可交付版本：** **大阪—京都铁路可视化 + 多运营商路线比较 + 基础运费展示 + 已乘区间点亮**。从一个数据可控、差异清晰的场景验证产品体验，再逐步扩至日本全国。

## 1. 目标与边界

### 1.1 核心用户问题

1. **怎么到达？** 不同铁路公司、不同站点和换乘方案的耗时、费用与便利度如何比较？
2. **为什么这样走？** 列车直通关系、站台、线路归属、票价构成、转车时间及适用票券如何解释？
3. **我坐过什么？** 已乘区间、车站、车型、到访市町村如何以统一规则记录并可视化？
4. **值得收藏什么？** 旅行轨迹、车票样式、车站印章、摄影作品与列车记忆如何长期留存？

### 1.2 产品原则

- **准确胜过覆盖。** 覆盖不足可以公开标记；不能展示编造的实时位置、价格或站内结构。
- **线路图 ≠ 行驶服务图 ≠ 运价规则图。** 从数据模型开始分开处理。
- **把「可解释」当成产品功能。** 路线推荐和价格应能展开查看依据及费用组成。
- **历史与现况均保留版本。** 线路、票价、车辆、票券、运营归属都会随时间变化。
- **以原创设计致敬铁路语言。** 可借鉴线路色、站号和日式公共交通信息层级；商标、站内图、车票版式和图像素材必须获得适当使用权。
- **数据归用户。** 基本足迹可免费记录和导出；账户/同步/高级统计应清楚定义隐私与定价边界。
- **预期效果与已实现能力分开。** 产品对外展示必须标注概念效果、样例数据与真实数据。

### 1.3 不在首版承担的目标

不承诺全国各公司的实时列车逐列定位；不自研完整全国列车时刻路由 + 铁路运价规则引擎；不做全日本大型车站高精度 3D 室内导航；不支持真正售票或生成可过闸机的有效票券；不把可能的近郊区间、分割运费节约视为普遍适用。

### 2.1 铁路百科的对象详情

**线路页面：** 中文/日文/英文名称、运营商、线路色、路线地图、区段与里程、车站顺序、站号、线路运营状态、直通运营关系、服务种别、经过本线的车型/编组、历史沿革、本人已乘区段、可用通票、关联票价方案。

**车站页面：** 所属行政区、运营商和换乘线路、各线站号、站台与楼层、出入口、主要设施、无障碍通路、授权平面图、换乘耗时说明、服务异常、周边景点与拍摄点（后期）。

**列车页面：** 车次/种别、运行路线与停站、运行日期、车型和座席等级；若有实时或推算位置，必须明确区分。

### 2.2 换乘案内与路线策略

用户输入出发点、目的地、出发/到达时间、人数/可选席别及偏好；系统可返回多条**来源可追溯**的方案。每张方案卡展示：起终车站（不要将大阪站和大阪梅田站当作同一实体）、时长、车次区间、换乘与步行距离、票价总额、费用组成、可能的通票抵扣、数据更新时间及来源。

- **示例场景：** 大阪→京都，至少比较 JR 大阪→京都、阪急大阪梅田→京都河原町；随后再考虑京阪沿线和真实门到门目的地。
- **多策略：** 快速抵达 / 费用最低 / 尽量少换乘 / 尽量少步行 / 无障碍优先 / 指定通票优先。
- **风险信息：** 转乘距离、候车时间、末班车、天气/延误（若有可靠数据）。风险可定性解释，不假装精确预测概率。
- **现实约束：** 高速与普通线路可能使用不同车站、站台、检票口；不同运营公司的穿越与票价应分离建模。

### 2.3 票价与票券研究室

#### 票价拆解（目标）

```
线路方案
├─ 基础乘车运费（乗車券 / 普通運賃）
├─ 特急附加费（特急料金，适用时）
├─ 指定席 / 座席等级附加费（适用时）
│  ├─ グリーン料金
│  └─ グランクラス料金
├─ 跨公司、不同票制或补票项目（如适用）
├─ 通票覆盖/抵扣（附规则及例外）
└─ 最终应付金额 + 计算依据 + 数据版本
```

#### 必须分开建模的铁路票制概念

- **大都市近郊区間：** 特定条件下实际乘坐路径与普通运费计费路径可能不同；不意味着所有绕行都可行，也不代表自由途中出站。
- **幹在同一視：** 某些新干线与并行在来线在基础运费规则中视作同一线；需针对适用区间和例外逐项建模。
- **特定都区市内：** 「東京都区内」等并非起终站任意显示；需满足指定距离和票制条件。
- **分割乗車券：** 连续旅程分多段购票时，须核验区间连续、购买与乘车条件、是否实际降价、是否允许中途出站等；不能自动推荐不合法方案。
- **途中下車：** 应按票种、里程、有效期和地域限制处理；乘车券与附加票不能混为一谈。
- **通票：** 覆盖的公司、线路、车种、席别、有效日及特殊补票必须逐项验证。

**实现纪律：** 票价由确定性规则或取得授权的服务计算；语言模型可辅助解释，但不直接编造可购买票价。

### 2.4 个人足迹「全日本制霸」

至少区分四类独立进度：**已乘坐线路区间 / 已到访车站 / 已乘坐车型 / 已到访市町村**。可扩展公司覆盖率、都道府县数、里程、车次与年代。

**统计原则：**

1. 坐过一条线的某一段不等于全线完乘；线路应拆成可追踪的**区间/边**，计算真实覆盖长度。
2. 路过一座车站不等于实际在此上下车；乘车经过一个行政区也不等于「到访」。
3. 行程可手动补录历史记录；自动推断必须可人工确认、编辑和删除。
4. 线路拆分、改名、废线和运营归属改变时，既有历史记录需要保留当时版本，并映射到当前显示。
5. 用地图点亮、行程时间线、个人徽章、旅程海报和年份回顾表现成长，但不将娱乐统计伪装成官方认证。

### 2.5 数字车票博物馆

- 对乘车记录生成**纪念性质**的模拟票；支持不同时代/铁路公司的视觉主题，需合法获得设计与素材使用权。
- 字段可包括：日期、列车、起终站、实际票面表示（可能为「東京都区内」类区域名）、座席等级、乘车券/特急券关系、票面备注、途中下車规则等。
- 票面是**可分享收藏卡，不是真车票**。始终有显著的「SAMPLE / 記念用 / 不可乘车」标记；不得输出可被设备验真的 QR、条码或磁条编码。
- 可链接行程照片、车站印章和所乘车型，形成一段旅行的数字纪念册。

### 2.6 差异化扩展

铁路摄影模式、车站印章、历史线路时间轴、可视化通票回本、离线数据、无障碍与换乘风险、未乘铁路补全路线、乘坐车型收藏等均纳入长期路线图，但需分别确认数据来源、授权、需求强度和维护成本。

## 3. 信息架构和用户体验

### 3.1 Web / 移动端建议导航

| 一级入口 | 主要内容 | 第一屏应回答的问题 |
|---|---|---|
| **地图 Atlas** | 全日本/区域铁路地图、线路/车站弹层、直通关系 | 这里都有哪些铁路？ |
| **出行 Journey** | 目的地搜索、时刻、方案比较、票价详情 | 我要怎样到达？ |
| **票券 Tickets** | 票价计算、Pass 选择、纪念票博物馆 | 需要付多少钱、能否用通票？ |
| **足迹 My Rail** | 线路点亮、完成度、轨迹、列车收藏 | 我已经走过哪里？ |
| **我 Profile** | 账户、同步、隐私、数据导入/导出 | 如何保存和管理自己的记录？ |

### 3.2 核心体验闭环（应在设计稿中体现）

`地图点选阪急京都线` → `查看站点/直通/车辆/票券` → `规划大阪→京都` → `比较 JR 与阪急` → `实际乘坐后确认区段` → `地图高亮` → `生成带车票与照片的旅程卡片`

### 3.3 设计语言

- 原创、克制、信息密度可控的日式交通信息设计；线路色用于识别而不是铺满背景。
- 线路、车站、站号、运行种别、箭头和换乘关系必须有一致的图形语法；无障碍、多语言与深浅色主题自始考虑。
- 参照 Rail Typing 的舒适感与系统性，不直接复制其素材、图标、声音或页面。
- **动态效果用于理解：** 地图平滑高亮、路线推演、区间点亮、票面收藏；不牺牲低端手机流畅度。
- 站内 3D 作为特定枢纽的深度展示，而非基础信息唯一入口。

## 4. 数据、授权与可靠性（硬约束）

### 4.1 数据类型及来源候选

| 数据域 | 可能的数据来源/获取策略 | 开发前必须确认 |
|---|---|---|
| 运营公司、路线/站点、地理几何 | 自建整理；国土数值情報等许可合适的数据 | 每个数据集的商用、再分发、衍生作品限制 |
| 时刻表与实时运行 | ODPT、运营商接口、授权第三方 | 覆盖运营商、更新周期、缓存与展示权利 |
| 路线查询与票价 | 駅すぱあと等专业 API 或合规自建 | 商用费用、API 权限、转存/用户量限制、精度 |
| 站内图/出口/设施 | 运营商公开素材、合作授权、自建勘验 | 原图版权、更新维护、是否允许修改与缓存 |
| 车辆资料、票券、历史 | 官方资料、取得授权的图像/独立创作资料 | 图像、商标、票面形象及历史数据的权利 |
| 用户位置/足迹/照片 | 用户主动录入，基于同意的设备数据 | 最小权限、加密、删除与导出、默认私密 |

**特别风险：** 原讨论指出国土数值情報的部分铁路时序数据存在商业许可限制。该提醒应作为许可核查清单，不应在确认具体数据集条款之前直接采集商用。

### 4.2 数据对象建议

- `Operator`：运营公司（身份、品牌属性、生效日期）
- `RailLine`：线路名义实体（公司、展示颜色、历史版本）
- `TrackSegment`：轨道几何区段/里程，可与多个线路实体关联
- `Station` / `StationComplex` / `Entrance` / `Platform`：车站、换乘复合体、出口及站台
- `ServicePattern` / `Trip` / `StopTime`：运营服务、实际车次、停站时刻
- `ThroughService`：直通服务跨线路/公司的关系及适用日期
- `FareRule` / `FareProduct` / `FareQuote`：版本化运价规则、票种、报价和组成
- `PassProduct` / `PassEligibility`：通票、覆盖区间、车次/席别限制
- `VehicleSeries` / `Formation`：车型与编组、运营时期
- `RideRecord` / `RideSegment` / `VisitedStation`：用户行程与区间覆盖
- `CommemorativeTicket`：关联行程的模拟纪念票面，不存储有效检票凭证
- `SourceRecord`：数据来源、许可、抓取/校验时间和有效期间

必须支持 `valid_from` / `valid_to` 的业务时间；必要时还保留数据观察/导入时间，以便追踪过去某次报价从何而来。

### 4.3 线路图不等于运价图

1. **轨道拓扑图**：两站之间有没有铁轨、轨距/线路关系如何；
2. **运营时刻图**：什么车在何时到站、可否换乘，可能跨公司直通；
3. **计费规则图**：根据票种和适用规则按什么路线、何种距离计费。

三者共用统一标识、彼此关联，但**不能用一个简单的图和最短路算法覆盖全部逻辑**。

### 4.4 数据质量基线

任何可见的实时报价、列车状态和时刻表须至少给出：**来源、更新时间、适用日期、覆盖范围、数据性质（实时/时刻表/估算）**；若缺失，展示「暂不支持/需要核对」，不展示看起来精确的编造结果。

## 5. 技术架构草案（可在开发验证后调整）

**建议技术主线：TypeScript 为核心，Web + 移动端复用业务模型。**

```text
                  Japan Railway Atlas
       ┌────────────────────────────────────┐
       │ Web: React / Next.js               │
       │ iOS & Android: Expo / React Native │
       └───────────────┬────────────────────┘
                       │ 共享 TypeScript 类型 / 规则
             API / 身份 / 账户服务
                       │
       ┌───────────────┼───────────────────┐
       │               │                   │
 铁路知识图谱      路线规划/票价层         个人记录服务
       │               │                   │
 PostgreSQL + PostGIS  授权 API/规则引擎    账户/足迹/收藏
       │               │                   │
       └─────────数据版本/来源/许可记录───────┘
```

- **地图：** MapLibre GL JS；移动端选对应的 MapLibre 方案并验证性能与交互一致性。
- **地理数据库：** PostgreSQL + PostGIS；地理线段、站区及用户点亮区段需要空间查询。
- **路由：** 原型优先用合规服务验证体验；自研动态换乘查询时研究 RAPTOR / Connection Scan Algorithm 等适用于时刻表网络的算法。
- **运价：** 独立、可测试、确定性的票价规则引擎；时间版本和地区例外是基本功能。
- **数据接入：** 针对每个运营商或服务商设适配器；保留错误/缺失/许可状态，不把来源数据直接写死到前端。
- **账户：** 支持匿名本地探索及登录后的同步；提供导出格式和数据删除控制。

这是**建议架构**，不是已确定的技术决策。框架版本、授权、云成本及移动端表现需通过 Prototype 验证。

## 6. 分期研发路线与验收条件

### Stage 0 · Discovery / 数据与交互验证

**交付物：** 一套大阪—京都站点与线路最小数据包；可验证的来源和许可清单；三端体验草图；定义线路/区间/服务/票价的 ID 规范。

**通过标准：** 至少能明确区分 JR 大阪站、阪急大阪梅田站、JR 京都站和京都河原町站，且能够回答「本次展示的票价从哪里来、什么日期生效」。

### Stage 1 · Prototype（首个可展示作品）

**范围：** 可交互关西线路图；运营商、站点、线路详情；JR/阪急直观分色与路线对照；直通关系基础展示；原创设计系统。

**通过标准：** 地图操作流畅，用户能点选一个站和一条线，正确看到实体关系与经过区段；不将样例时刻当实时。

### Stage 2 · MVP（首个核心价值闭环）

**范围：** 大阪—京都多路线比较、基础合法运费展示、源数据时间戳、手动记录已乘区段、地图点亮及进度统计；基础本地存储/导出。

**通过标准：** 用户能够完成 `查路线 → 比较费用和耗时 → 选择 → 标记已乘 → 地图点亮`；跨公司站点差异可解释；票价缺失时准确提示。

### Stage 3 · Beta（可让真实用户持续使用）

**范围：** 多端账户同步、车站细节补强、车型图鉴、模拟纪念票、更多地区、通票信息与旅行回顾。

**通过标准：** 测试用户能多次累积足迹；增删记录一致；不同设备同步后不丢失区间覆盖；纪念票不可作为有效车票。

### Stage 4 · V1（逐步扩大商业服务能力）

**范围：** 经授权扩大全国线路/时刻/票价覆盖；监控数据更新；显示部分运营状态；标准化后台质检；收费功能小范围验证。

**通过标准：** 每个承诺支持的运营商/路线都有明确数据覆盖、有效期与错误处理；收费服务具备数据导出、备份和隐私保护。

### Stage 5 · 长期扩展

高级分割运费、票价与通票计算、历史地图、全站 3D、摄影模式、离线旅行包、铁路补完推荐、站章社区等分别按收益和数据可得性安排。

## 7. 第一轮开发任务池（建议）

| 顺序 | 任务 | 完成判据 |
|---|---|---|
| 01 | 明确产品名/定位与主导航 | 一页定位说明 + 关键用户流程图 |
| 02 | 制作关西铁路数据许可矩阵 | 每个初始字段均能追溯来源及可商用范围 |
| 03 | 定义 Station、Line、Segment、Service、Fare 领域模型 | 提供示例 JSON/类型，ID 不混淆 |
| 04 | 建立大阪—京都的人工核对测试数据 | 运营公司、站点与线路关系经人工复核 |
| 05 | 绘制线路地图及图例 | 站名、颜色、缩放和区间选择可用 |
| 06 | 完成站点、线路详情 UI | 站点/公司/区间关系能互相跳转 |

| 08 | 接入来源明确的基础运费报价 | 显示有效期、错误状态、报价来源 |
| 09 | 用户手动标记已乘区间 | 可编辑、撤销、持久保存并正确点亮 |
| 10 | 完成 3 端原型适配和体验测试 | 手机、桌面地图/交互都能完成闭环 |

### 必测场景

- **大阪—京都：** JR 与阪急站名和线路不同；不能仅因城市名相同就视为等价终点。
- **直通列车：** 跨运营商不停换乘，也可能涉及不同票价计算/边界。
- **特殊票制：** 「東京都区内」、大都市近郊区间、幹在同一視、途中下車、分割乗車券，逐一做带条件的测试用例；不能由词语触发固定优惠。
- **票券：** IC/纸票、特急券、指定席、グリーン、グランクラス、Pass 适用与补差价。
- **个人制霸：** 只坐某线 20% 不算 100%；经过某市不自动算到访；重新命名或废线不能抹掉历史。
- **状态与来源：** 第三方 API 失败、数据过期、仅有时刻表推算、运营商无实时数据时都应给出正确提示。
- **模拟车票：** 强制显示非有效标识，不输出可能验证的编码。

## 9. 商业化与用户信任

**原讨论建议：Freemium**，而不是把第一次足迹记录完全锁在付费墙外。

- **Free（方向）：** 基础查线、地图/车站资料、有限或基础路线查询、手动足迹和基础完成度、数据导出。
- **Railway Pro（方向）：** 深度统计、跨端高级同步/备份、旅行回顾、可视化收藏、特色纪念票、补全路线等。
- **试探性定价（非最终）：** #7 曾建议 ¥300–500/月；仅作待访谈验证的假设，非已经定价或已证实愿付价格。
- **成本与合规：** 授权 API、云计算与地图成本、账户安全、支付和退订、数据保留/删除、客服维护须作为商业模式的一部分。

**关注指标（非既定目标值）：** 初次线路标记率、用户第二次记录率、一个月活跃留存、地图与路线查询使用占比、足迹数据的成功导出率、报价错误率和过期率。
