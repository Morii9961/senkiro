写于 2026-11-11。本报告里的构建、测试和性能数字都是当天在本机真实运行得到的。

## 1. 一句话结果

Must 七项和 Should 三项全部完成，Could 两项没做：做出了一个 JR 东日本新宿站加京王线新宿站的五层示意模型，3D、2D 平面图和寻路图由同一份手工录入的数据生成，`npm install && npm run build && npm test` 在干净目录里通过（84 条单元测试、15 条端到端测试）；但数据是 AI 对照官方图录入的，没有人复核，几何全部是示意。

## 3. 范围完成情况

### 建模范围与几何精度

- **建模**：JR 东日本新宿站 B1F、1F、2F；京王线新宿站 B1F、B2F。共 5 个楼层、33 个区域（其中站台 9 个）、18 个检票口、12 个出入口、72 条垂直设施、9 条通道。
- **只画体块**：小田急线新宿站、东京地铁丸之内线新宿站、都营新宿线・京王新线新宿站、都营大江户线新宿站、バスタ新宿、京王临时口的出口侧，共 6 个，全部标「未核实」，不进寻路图。
- **不在模型里**：西武新宿站、新宿三丁目站、新宿西口站（都是别的车站）。
- **几何精度**：没有任何一个元素的几何是 `verified`。127 个元素是 `schematic`（相对位置大致照 JR 的图，尺寸自拟），28 个是 `unknown`（京王的 21 个元素、1 条推断出来的连接和 6 个体块，位置只是占位）。所有坐标和楼层高度都是自拟的「示意单位」，不是米。楼层之间的高度差是为了看得清统一设的，只有上下顺序取自资料。

## 6. 与任务书的事实出入

1. **分支名**。任务书写「当前分支 lab/c-shinjuku-3d」。实际会话所在的 git worktree 检出的是 `claude/shinjuku-3d-indoor-nav-3f3cce`；`lab/c-shinjuku-3d` 存在，但被另一个 worktree 占用。按契约 §8「只在当前分支工作」，所有提交都在 `claude/shinjuku-3d-indoor-nav-3f3cce` 上，没有碰 `lab/*` 分支。
2. **JR 东日本的链接打不开**。`https://www.jreast.co.jp/estation/stations/866.html` 及其图片从本环境访问一律返回 HTTP 403。改读 Internet Archive 的快照（页面 2026-09-25，图片 2026-09-15）。因此**无法确认**官网今天的内容是否和快照一致。快照上的图印着「2026年8月現在」。
3. **「京王新宿站」其实是三样东西**。京王的页面把「京王線新宿駅」「京王新線新宿駅」「新宿ターミナル」分开列，前两者各有各的构内图。本原型只建了「京王線新宿駅」。
4. **京王的资料比 JR 的旧约 17 个月**。京王构内图印「2025年3月末現在」，JR 的是 2026 年 8 月。两家的边界（京王線連絡口一带）是用两张不同时间的图拼起来的。
5. **小田急的链接能打开，但内容没有读**。任务书允许京王和小田急二选一，选了京王。
6. **ODPT 确实有新宿站的设施数据，但不能用**。ODPT 目录里有「歩行空間ネットワークデータ（JR東日本 新宿駅）」和构内地图数据（目录页写最后更新 2026/10/26），许可是挑战赛限定许可加 JR 东日本特定条件：只限挑战赛、禁止再分发、2027-03-12 到期。实时运行信息的数据集同样如此。两者都没有下载。
7. **「paid / unpaid」两分法不够用**。新宿站有 JR 和京王两个各自独立的付费区，之间隔着换乘检票口；京王那一侧还有一道 JR 自己的检票口「JR中央西改札（京王口）」。模型把付费区按运营商区分，「只经 Gate 相连」的约束同样适用于两个付费区之间。
8. **「JR 新宿站 2F」不是一个连通的付费区**。JR 的 2F 图上有两块互不相连的付费区（南口站厅；新南・甲州街道・ミライナタワー检票口内的站厅），在 2F 这一层没有画付费通道相连。模型里它们只能经站台往返（有测试）。
9. **5・6 番线站台是单独靠南的**。它和北侧、中央两处 B1F 站厅之间没有直接的楼梯，JR 的立体图上印着「⑤・⑥番線への乗り換えは約10分ほどかかります」。这句话只抄在该站台的备注里，本原型不把它当作路线时间输出。
10. **没有发现「跨越不相邻楼层」的垂直设施**。任务书的测试要求里提到「相邻或声明连接的楼层」。本模型里跨度最大的是电梯 G（B1F、1F、2F 三层都停），没有哪个设施跳过中间楼层。「声明非相邻连接」的机制和校验都实现了，但只用构造的反例测试过。

## 7. 已知缺陷与风险

### 数据可靠性

- **没有人复核，也没有实地核对。** 全部数据由 AI 编码代理读图录入。读图可能读错，尤其是密集的楼梯和扶梯符号。把它用于任何面向乘客的用途之前，必须有人对照官方图逐条检查 SOURCES.md 的核对表。
- **车站在施工。** JR 的三张图都印着改良工事的提示。资料日期之后的变化不在模型里。
- **扶梯方向未知。** 官方图不标扶梯的运行方向，京王的图还印着随时段变化的方向。默认模式优先选扶梯，所以算出的路线可能包含一段实际上逆向的扶梯。路线 1 的最后一段和路线 3 的最后一段都是扶梯，方向未经确认。
- **开放时间没有参与寻路。** 检票口和电梯的开放时间（如中央西改札「6:00〜終電」、東南改札「7:00〜24:00」、东口电梯「4:00〜25:30」）只记在备注里。只出不进的检票口（京王的广场口、临时口）是处理了的。
- **楼梯、扶梯是合并录入的**，数量没有记。京王的三条线合成了一个站台节点，京王的多台电梯合成了一条。
- **无障碍信息不完整。** `stepFree` 有很多是 null。「只走电梯」模式会放行这些路段并标出，不能当作无障碍保证。
- **线路颜色是近似色**；英文和中文名称是本原型的翻译，不是官方译名；假名读音和站号一律为空。
- **成田特快、东武线直通被存成了 RailLine**，按契约应该是 ServicePattern。

### 未确认的连接（没有进模型）

1. JR 中央通路（B1F）、南口站厅（2F）与小田急线之间的两个换乘口：只读了 JR 一侧。
2. 南口（南改札外）与甲州街道改札之间跨甲州街道的地面连接：是公共道路，JR 的图上没画成通道。
3. 新南改札、甲州街道改札、ミライナタワー改札三处检票口外的相互连接：图上是一片连续的非付费区，但没有逐条读出通道。
4. 東南改札外与南口之间在 2F 的连接：图上被ルミネ2隔开。
5. 中央西改札外与西口地下、京王线、小田急线之间的连接：JR 的图在检票口外只画了一个售票处。
6. 13–16 番线站台南端的一块区域：JR 的 1F 图用不同底色标出并写着「B1F 中央東改札・中央西改札」，立体图在 14、16 番线附近画了「小田急線連絡口」。没读明白，没有建模。
7. 京王线 3 番线站台与京王新线・都营新宿线 4・5 番线站台之间的连接：京王的图上有文字说明，但京王新线新宿站不在范围内。
8. JR B1F 与京王 B1F 的相对高度：连接通道里画了台阶，升降方向和高度都不清楚。
9. 新南改札外与バスタ新宿 3F、4F 之间的电梯和扶梯。

另有一条**推断出来、进了模型但带标记**的连接：西口地下 ⇄ 京王西口外。两家的图各自印了指向对方的文字，都没画中间的路。演示路线不经过它；寻路时可以禁用。

受这些缺口影响，模型里有些地方只能绕路到达，算出的路线可能比现实绕。

### 产品与工程

- **代价模型不等于「最快」。** 它偏好搭乘次数少的走法，所以路线 3 会选一台电梯连下两层。没有距离数据就没法做得更好。
- **帧率只在 headless Chromium 里测过**，没有真机数据；Firefox 和 Safari 没有运行过。
- **3D 分包有 948 kB**（gzip 后 251 kB），几乎全是 three.js。
- **无障碍只做到基本程度。** 所有控件能用键盘操作，画布能用键盘旋转缩放，WebGL 不可用时会退到 2D 并说明。但图上的单个元素只能用指针点选；键盘用户只能通过路线的逐段列表和运行面板里的站台链接打开元素详情。颜色对比度没有用工具审计过，也没有用读屏软件实测。
- **每加一个车站都要手工录入一遍。** 这次的录入方式不成规模。
- **官网条款没有审阅。** 「读官方构内图上的事实、自己重画示意图」这种做法在商业使用时是否有问题，本报告不下结论。

### 迁移到关西（大阪—京都）需要什么

以下只说方法；关西各站的具体情况**本次没有调查，不作任何事实陈述**。

1. **逐个运营商核对资料和许可。** 每家的构内图页面、能否访问、资料日期、使用条款，都要像这次一样逐条登记成 SourceRecord。ODPT 是否覆盖关西的运营商、各数据集是什么许可，需要另行核对。
2. **先定 StationComplex 的边界。** 关西的大型枢纽里，「不同名但能步行换乘」和「同名但不是同一个站」两种情况都要预期会遇到。`complex.explicitlyExcluded` 这种「明确写出哪些不算」的做法值得沿用。
3. **票务区模型可以直接用。** `paid:<operator>` 加换乘检票口的建法不依赖具体车站。运营商之间有没有不出站的换乘口，要逐站核对。
4. **楼层对齐要逐站做。** 各家楼层编号不通用，`ordinal` 只能逐站人工确定；确定不了的要像这次一样标「未知」。
5. **录入成本是瓶颈。** 这次一个站用了一整个会话。要覆盖大阪到京都沿线的主要枢纽，得先解决数据来源（有许可的结构化数据，或一个带复核流程的录入工具），否则不可持续。
6. **代码层面要改的很少。** 加一个 `data/manual/<车站>.ts` 和对应的来源记录，界面上加一个车站选择器；领域层、校验、寻路、渲染都不用动。界面文字目前是日、英、中三种。
