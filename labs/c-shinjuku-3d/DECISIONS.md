# DECISIONS · SENKIRO Lab · Shinjuku Station 3D

每条按「决定 / 备选 / 理由」记录。日期均为 2026-11-11。

## A. 范围与资料

### A1. 相连运营商选京王，不选小田急

- **决定**：第二个站区建京王线新宿站（B1F 站厅、B2F 站台）。小田急只画未核实体块。
- **备选**：小田急新宿站。
- **理由**：JR 的 B1F 图和京王的构内图能互相印证同一处连接——JR 印「京王線連絡口」，京王印「JR連絡口」；JR 印「JR中央西改札（京王口）」，京王印「JR中央西改札」。两张图对得上，边界就有据可依。小田急这边，JR 立体图自己写着「小田急電鉄・東京メトロは改良工事中のため、一部変更となる場合があります」，站区正在改建，资料最容易过期。任务书只允许选一个，所以小田急的页面虽然能打开（HTTP 200），内容**没有读取、没有使用**。

### A2. JR 官网打不开，改读 Internet Archive 的快照

- **决定**：JR 东日本的构内图页面和四张图，读的是 Wayback Machine 2026-09 的快照；SourceRecord 里 `url` 写官方原址，另加 `accessedVia` 写快照地址。
- **备选**：(a) 放弃 JR 官方图，改用第三方网站的转述；(b) 找人手工下载。
- **理由**：从本环境直接访问 `www.jreast.co.jp` 一律 HTTP 403。快照是官方页面的原样存档，图上印着「2026年8月現在」，比任何转述都可靠；(b) 违反 one-shot 不求助的约定。风险是快照可能不是最新版，已在 REPORT「与任务书的事实出入」和「已知缺陷」里写明。

### A3. 不使用 ODPT 的步行空间网络数据和列车运行信息

- **决定**：ODPT 上的「歩行空間ネットワークデータ（JR東日本 新宿駅）」和「JR東日本 鉄道関連情報」都不下载、不使用。
- **备选**：注册开发者账号取数，用它生成寻路图和实时叠加层。
- **理由**：两者都是「公共交通オープンデータチャレンジ限定ライセンス」加 JR 东日本特定条件：只限挑战赛用途，禁止再分发数据及可还原的衍生物，2027-03-12 到期，并排除与 JR 东日本竞争的服务。这和一个公开再分发的 AGPL 仓库不相容。契约 §1.8 规定拿不准就先不用，记入待决事项。

### A4. 官方图只读事实，几何全部重画

- **决定**：打开官方图阅读，只记下「名称、在哪一层、检票口哪一侧是付费区、什么和什么相连」；所有形状都是自己画的矩形，坐标自拟。图片不存仓库，也不放 `data/raw/`。
- **备选**：按官方图描轮廓；或把图片当底图垫在下面。
- **理由**：任务书明确禁止嵌入、描摹成高精度复制品或随仓库分发。仓库里因此没有任何图片、PDF 或字体文件，这一点有单元测试守着（`provenance.test.ts`）。

### A5. 西武新宿、新宿三丁目、新宿西口、京王新线新宿不进模型

> 2026-11-13：其中西武新宿站和京王新线新宿站已经进了模型，见 I1、I2。新宿三丁目和新宿西口仍然不进。

- **决定**：这四个只出现在 `complex.explicitlyExcluded` 列表和界面说明里。京王新线新宿站只包含在「都営新宿線・京王新線」那个未核实体块的名字里。
- **备选**：也画成体块。
- **理由**：前三个是别的车站，画进来就是任务书点名要避免的混淆。京王官网把「京王線新宿駅」和「京王新線新宿駅」分开列，各有各的构内图，所以按两个站处理。

## B. 数据模型

### B1. 「是否存在」和「几何是否可信」分成两个字段

- **决定**：每个元素有 `existence`（verified / unverified）和 `geometryConfidence`（verified / schematic / unknown）两个字段。
- **备选**：只用任务书要求的 `geometry_confidence` 一个字段。
- **理由**：「東改札存在于 B1F」是核实过的事实，「它画在 (-14.75, -10)」是我编的位置。只用一个字段，要么把事实说弱了，要么把坐标说强了。

### B2. 手工几何永远不许标成 verified

- **决定**：校验规则 `geometry-confidence` 拒绝任何 `manual-verified` / `synthetic` 元素自称 `geometryConfidence: 'verified'`。JR 元素一律 `schematic`（相对位置大致照图），京王元素和未核实体块一律 `unknown`（位置是占位）。
- **备选**：给看起来比较有把握的元素标 verified。
- **理由**：没有任何测绘数据。`verified` 这个值留给将来有合法测量数据的时候。

### B3. 付费区按运营商区分

- **决定**：`fareZone` 取 `'unpaid' | 'paid:jr-east' | 'paid:keio'`。两个不同的付费区之间也算「票务边界」，只能经换乘检票口（`gateKind: 'transfer'`）相连。
- **备选**：只分 paid / unpaid 两种。
- **理由**：只分两种的话，JR 付费区和京王付费区就能用一条普通通道连起来，京王線連絡口这道检票口会从模型里消失。任务书要求的「paid / unpaid」仍然是每个区域的一个明确属性。

### B4. 检票口画在两个区域之间的「检票线」上

- **决定**：Gate 不属于任何一个区域；它有两个 `sides`，位置落在两侧区域之间约 0.5 个单位的缝里。校验规则 `gate-position` 要求它离两侧区域都不超过 0.75 个单位。
- **备选**：把 Gate 放进其中一个区域里。
- **理由**：这样 3D 上能看见一条检票线，寻路图上检票口是一个独立节点，两者对应。一侧也可以是未核实体块（如小田急换乘口），这时那一侧不生成任何边，路线出不去。

### B5. 楼层按运营商各自建实体，用 `ordinal` 对齐上下

- **决定**：JR 的 B1F 和京王的 B1F 是两个 Level，都取 `ordinal: -1`。京王 B1F 在图上故意比 JR B1F 低一点（-4.7 对 -4），并在说明里写明「相对高度未知」。
- **备选**：合并成一个 B1F。
- **理由**：各家自己编楼层号。JR 的图在通往京王的通道里画了两段台阶，说明两边地面不在同一高度，但升还是降、差多少都读不出来。合并会制造一个没有依据的事实。此事列入「未确认的连接」。

### B6. 楼梯和扶梯按「站台 × 站厅」合并，电梯逐台录入

- **决定**：同一个站台岛通往同一个站厅的全部楼梯记为一条（`aggregated: true`），扶梯同理。JR 的电梯按图上印的字母 A–O 逐台录入，每台停哪几层照图。
- **备选**：逐个楼梯录入。
- **理由**：图上的楼梯符号又小又密，数量数不准；数错就是编造。寻路只关心「这一对之间有没有楼梯 / 扶梯」，这一点能读准。电梯有字母，位置和停靠层都清楚，而且无障碍路线必须精确到台。扶梯的运行方向图上没有，记为未知。

### B7. 京王站台合并成一个节点

- **决定**：京王 1–3 番线的几块站台板（含降车专用站台）合成 `sk:area:keio-b2f-platforms-1-3` 一个节点。
- **备选**：按站台板拆开。
- **理由**：哪块板对应哪条线、哪台电梯通哪块板，我没有把握抄对。合并后的说法「京王站厅 B1F 经楼梯 / 扶梯 / 电梯到 B2F 站台」是能核实的。

### B8. 图例里的「成田エクスプレス」「東武線直通」暂记为 RailLine

- **决定**：JR 图例把 5・6 番线标成这两种列车。模型里先当作 RailLine 存，颜色用中性灰，并加说明：按契约它们应该是 ServicePattern。
- **备选**：现在就引入 ServicePattern。
- **理由**：本原型不涉及运营服务图。硬造一个半成品的 ServicePattern，不如如实标注「这里借用了 RailLine」。

### B9. 线路颜色是近似值，站号和假名一律为 null

- **决定**：`displayColor` 取官方图例色条的近似色，带 `displayColorNote` 说明「不是官方色值」；京王线的颜色是本原型为对比度自选的。`stationNumberPrefix` 和所有 `ja_kana` 都是 null。不使用任何线路符号或 Logo。
- **备选**：填上通常认为的官方色值、站号和读音。
- **理由**：这些我没有对照来源核实过。契约 §1.2：不知道就写 null。

### B10. 名称：日文照抄，英文和中文是原型译名

- **决定**：`names.ja` 是资料上印的原文；图上没有名字的区域 `ja` 为 null 或用描述性名称并在备注里说明。`en` / `zh` 是本原型的翻译，不是运营商的官方译名。
- **备选**：只留日文。
- **理由**：契约要求界面至少支持日英。官方英文站内图没有读取，所以译名的性质在这里和 REPORT 里都写明了。

### B11. `dataNature` 用 `manual-verified`，并写明录入者是 AI

- **决定**：对照官方图录入的元素标 `manual-verified`，同时在数据文件开头和 REPORT 里写明：录入者是 AI 编码代理，没有人复核过。
- **备选**：标 `derived` 或 `unknown`。
- **理由**：契约对 `manual-verified` 的定义是「人工对照官方资料录入，需记录对照的页面」，过程符合，页面都有记录。但读者默认会以为「人工」是指人，所以必须把实情写出来。

### B12. 资料日期用 `asOf`，`validFrom` / `validTo` 留空

- **决定**：每个元素带 `asOf`（资料上印的日期：JR 是 2026-08，京王是 2025-03）。契约要求的 `validFrom` / `validTo` 保留但为 null。
- **备选**：把资料日期填进 `validFrom`。
- **理由**：「这张图是 2026 年 8 月的」不等于「这个检票口从 2026 年 8 月起有效」。启用和停用日期没有来源。

## C. 寻路

### C1. 寻路图由同一份模型现算

- **决定**：`buildGraph(model)` 是纯函数。浏览器里用它从 `station.json` 现算寻路图；仓库里提交的 `graph.json` 只是给人看和给测试比对用的。
- **备选**：单独手写一份图数据。
- **理由**：任务书点名的陷阱是「3D 模型与寻路图不一致」。同源生成之外，还有 `checkModelGraphConsistency` 校验（画出来的元素必须在图里，图里的节点必须画出来）和单元测试双向检查。

### C2. 节点和边的种类

- **决定**：节点四种：区域、检票口、出入口、垂直设施在某一层的停靠点。边五种：通道、到检票口、到出入口、到设施停靠点、设施内部（唯一能换楼层的边）。
- **备选**：只用区域当节点，检票口和设施当边。
- **理由**：检票口和设施当节点，「付费区内外只能经 Gate」「只有垂直设施能换层」就都能写成对图的简单断言，路线输出里也能直接点名经过了哪个设施。

### C3. 代价不含距离和时间

- **决定**：代价是一个按字典序比较的五元组：过检票口次数、楼层变化次数、搭乘设施次数、段数、偏好（默认模式下扶梯优先于楼梯优先于电梯）。结果里 `distanceMeters` 和 `durationMinutes` 固定为 null。
- **备选**：用示意坐标算欧氏距离，再折成分钟。
- **理由**：坐标是编的，由它算出来的米数和分钟数也是编的。任务书要求用「段数、楼层变化次数、是否经过检票口」。把过检票口放在第一位，是因为多过一道检票口在现实里可能意味着多付一次钱。
- **副作用**：默认模式会偏向「一次搭乘跨两层」的走法。比如演示路线 3 从 2F 到 B1F 选了电梯 G（搭一次），而不是先下到站台再下一层（搭两次）。这是代价定义的直接结果，不代表现实里更快。

### C4. 「只走电梯」模式的含义

- **决定**：该模式只允许电梯，并拒绝任何 `stepFree === false` 的通道和检票口。`stepFree` 为 null（来源没说）的同层通道仍然允许，但路线结果里会单独列出这些「无障碍状态未经来源确认」的路段。
- **备选**：null 一律拒绝。
- **理由**：JR 图上的红色无障碍动线只画了一部分区域，一律拒绝会让大多数起终点无解。放行但逐条标出，比静默放行或静默拒绝都诚实。能验证这个模式的证据是：它算出的 東改札 → 5・6 番线 路线，和 JR 在 B1F 图上印的文字说明（Ⓖ → 2F → ⒶⒸ → ⒷⒹ → Ⓔ）一致。

### C5. 一条「推断」的连接进了图，但带标记

- **决定**：西口地下 ⇄ 京王西口外 这条通道标 `connection: 'inferred'`。路线用到它时那一段会标「推断」，`allowInferred: false` 可以禁用。
- **备选**：不收录。
- **理由**：两家的图各自印了指向对方的文字（JR：「京王線へ」；京王：「JR線・小田急線 東口方面」），但都没画中间的路，而且这一带在施工。不收录的话，JR 检票口外和京王检票口外完全不连通，显然不符合现实；收录又不能冒充已核实。演示路线都不经过它。

### C6. 读不准的连接一律不连

- **决定**：九处「资料有暗示但没读准」的连接不进模型，列在 `unconfirmedConnections` 里，界面「来源」面板可见（REPORT 第 7 节逐条列出）。
- **备选**：按常识连上。
- **理由**：契约 §1.1。后果是模型里有些区域只能绕路到达，例如两个 2F 付费区之间只能经站台往返。

## D. 3D 与界面

### D1. 手写几何合并，不用 drei

- **决定**：`buildPrims()` 把模型变成一组方盒图元，再合并成 4 个 BufferGeometry（不透明面、半透明面、轮廓线、路线），一共 4 次 draw call。相机控制用 three 自带的 OrbitControls。
- **备选**：每个元素一个 `<mesh>`；或引入 @react-three/drei。
- **理由**：200 多个元素各自一个 mesh 就是 200 多次 draw call。图元生成是纯函数，不依赖 three，可以在 Node 里做单元测试（「画的东西和模型一一对应」就是这样测的）。少一个依赖也少一份许可证要查。

### D2. 按需渲染

- **决定**：`frameloop="demand"`，只有镜头动或数据变时才画。加 `?perf=1` 才持续渲染。
- **备选**：每帧都画。
- **理由**：场景是静态的，没有动画（也不许有假列车动画）。静止时不耗电，对手机友好。

### D3. 标签用 DOM，不用 3D 文字

- **决定**：标签是叠在画布上的 HTML 元素，每帧投影定位；按「每个模型单位占多少屏幕像素」分四级显示，再做贪心碰撞剔除。标签不接收指针事件，点击由场景容器按记录的标签矩形判定。
- **备选**：SDF 文字（troika）或 Sprite。
- **理由**：日文和中文需要系统字体，DOM 文字清晰、可被读屏读取、不用打包字体文件（字体也有许可问题）。标签一开始能接收指针事件，结果滚轮滚到标签上时镜头不缩放——端到端测试抓到了这个问题，于是改成现在这样。

### D4. 避免 Z-fighting 的办法

- **决定**：同一层上叠放的面各占不同的高度，不共面；不透明面开 polygonOffset；半透明面不写深度；路线关闭深度测试并最后画。相机 near=2、far=1400。另有单元测试断言「同一层没有两块共面且重叠的水平面」，校验规则也拒绝同层区域重叠。
- **备选**：对数深度缓冲。
- **理由**：从数据上消灭共面，比靠渲染技巧遮掩更可靠，而且能测试。

### D5. 路线的折线只是画法

- **决定**：路线在区域内部的走线由 `routePoints()` 生成：相邻区域之间走共用边的中点，区域内部走直角折线，保证不穿墙。这些折点只影响画，不进寻路图，也不代表实际走法。
- **备选**：直接连节点。
- **理由**：直接连会穿过别的区域，看起来像是能穿墙。单元测试检查三条演示路线的折线全程落在画出来的区域内。

### D6. 2D 视图是每层一张 SVG

- **决定**：2D 模式下每个楼层一张 SVG 平面图，共用同一个坐标框，北在左（和 3D 默认视角一致）。文字和标记按屏幕像素定大小。
- **备选**：把 3D 相机切到正交俯视。
- **理由**：SVG 文字清晰、可缩放，每张图带文字替代说明，WebGL 不可用时也能用。它读的是同一份模型和同一条路线结果。

### D7. 未核实体块的画法

- **决定**：半透明、顶面带斜线纹（制图里表示「未测绘」的画法），标签固定带「未確認 / UNVERIFIED / 未核实」。它们不进寻路图，不能当起终点；位置、深度、大小都是占位。可以在「楼层」面板里整体隐藏。
- **备选**：不画。
- **理由**：任务书要求其他站区用抽象体块表示并醒目标注。把它们画得和已核实的部分明显不同，才不会被当真。

### D8. 运行叠加层：只有示例模式，时间戳故意是假的

- **决定**：`OperationOverlayProvider` 接口返回 `ok` 或 `unavailable`（带原因）。示例数据的时间戳固定为 `2000-01-01T00:00:00+09:00`，每条文字都带【サンプル】前缀，界面上有常驻的黄黑条纹横幅。接口里没有「列车位置」字段。ODPT 适配器不联网，只返回 `license-restricted` / `missing-key` / `not-implemented`。
- **备选**：示例数据用当前时间；或从公开时刻表推算。
- **理由**：用当前时间的示例数据截图后就像真的。没有位置字段，就不存在画假列车的入口。ODPT 的密钥按契约只能放在仓库根目录 `.env.local`，而本原型没有服务端，密钥进了浏览器包就等于公开，所以适配器要求的是「服务端代理地址」而不是密钥本身。

### D9. 语言、字体、底图

- **决定**：界面支持日文、英文、中文；只用系统字体；不用任何地图底图。
- **备选**：引入 Web 字体；垫 OSM 底图以表现出入口和街道的关系。

## G. 界面

### G1. 楼层按位置分组，不按运营商

- **决定**：界面上的楼层是「所有 `ordinal` 相同的 Level」，名称由位置导出（B2F、B1F、1F…）。数据里各运营商各自的 Level 不变。

- **理由**：用户明确要求去掉。乘客想的是「地下一层」，不是「京王的地下一层」。代价是界面不再提示「两家的 B1F 未必同高」——这句话仍在数据和「未建模的连接」里。

### G2. 站台必须带线路名

- **决定**：站台的名称、起终点列表、标签都带线路名；站台标签上有线路色块。
- **理由**：番线号在不同运营商之间重复（JR 有 1·2 番线，京王有 1–3 番线）。去掉运营商标识之后，线路名是唯一能区分它们的东西。有测试保证每种语言下站台名称互不相同。

### G3. 线路标识是自己设计的色块

- **决定**：线路色的圆角色块，核实了线路字母代号的才在里面显示代号；现在一个代号都没核实，所以全是纯色块。
- **备选**：照官方的线路符号画。
- **理由**：用户要「线路的图标」，契约 §6 禁止复制运营商的线路符号。折中是自己的图形加事实性的代号；代号没核实前不显示。

### G4. 只有设施有详情，而且不显示内部字段

- **决定**：站台、检票口、出入口、电梯、楼梯、扶梯和未核实体块有详情卡；站厅和通道点了没有反应。卡片只留乘客关心的内容，来源压成一行（运营商、资料日期、「位置为示意」）。
- **理由**：用户的原话是「这是要面向用户的」「站厅通道不需要详情界面」。契约要求每条可见数据可追溯，所以来源那一行不能删；完整的来源列表仍在「来源」面板。

- **决定**：去掉 2D 的「全部楼层」纵向排列，平面图铺满画面。
- **理由**：滚轮既是页面滚动又是图的缩放，两者冲突，用户建议直接删掉。

### G6. 三种楼层显示方式和「步骤聚焦」

- **决定**：全部楼层、单层、只看路线经过的楼层。点路线的某一步，镜头飞到那一段，只把那一步涉及的楼层画实，并把高于它起点的楼层画成半透明。
- **备选**：沿路线第一人称播放。
- **理由**：规格 §5.4 要求自动聚焦并明确不要第一人称。上层半透明是因为 1F 的站台正好压在 B1F 的通道上方，不这样做路线会被整层挡住。

## H. 3D 画法

### H1. 墙、柱、台阶、闸机、轨道是按规则生成的

- **决定**：这些构件不进数据，由 `src/ui/scene/arch/` 从区域轮廓和连接关系生成：墙沿区域边界，在检票口、出入口和有通道相连的相邻区域处开口；楼梯和电梯穿过楼板处开洞；轨道只画在数据标明了「番线在站台哪一侧」的地方；柱只画在站台上，位置纯属装饰。
- **备选**：把墙和柱当作车站事实录入数据。
- **理由**：没有任何资料能支持它们的真实位置。生成规则保证它们和连通关系一致（有测试：检票口里没有墙、相连的区域之间没有墙），又不会被当成事实。界面「显示」面板里有一句说明。

### H2. 番线在站台哪一侧，是新加的一条数据

- **决定**：`PlatformTrack.side`。JR 的 16 条番线按「1F 图上自东向西编号」填了；京王的没填，所以京王站台旁不画轨道。
- **理由**：这是能从资料读出的事实，画轨道和线路色边条都要用它。读不出的不猜。

### H3. 阴影是烘焙的，不用阴影贴图

- **决定**：墙脚的渐变接触阴影和构件自下而上的明暗渐变都写在顶点里；没有实时阴影。
- **备选**：一盏平行光的阴影贴图。
- **理由**：楼层叠在一起时，上层楼板会把下层整个罩黑，上层的墙还会把影子投到下层地面上，反而妨碍读图。烘焙的做法没有运行时开销。

### H4. 只有金属和玻璃用 PBR

- **决定**：金属和玻璃用标准 PBR 材质加程序生成的环境反射；地面、墙、混凝土、涂装件用漫反射材质。不使用任何贴图或 HDR 图片文件。
- **备选**：全部用 PBR。
- **理由**：粗糙表面用不用 PBR 看不出差别，但软件渲染下全 PBR 在 1920×1080 只有约 5 FPS。仓库里不放图片文件这条规矩也因此保住了。

### H5. 相机的限制

- **决定**：俯仰角限制在 0.22–1.32 弧度（从正上方量），距离有上下限，目标点限制在模型周围的盒子里。左键旋转，中键和右键平移，滚轮缩放。镜头移动有 0.65 秒的动画，任何操作都能打断，可在「显示」面板关闭，系统设置了「减少动态效果」时默认关闭。
- **理由**：规格 §5.2。中键平移是用户点名要的。

### H6. 线路运行状况是从列车延误汇总出来的

- **决定**：ODPT 上 JR 东日本没有线路级的运行情报，只有逐列车的延误秒数。适配器把一条线路上在途列车的延误汇总成状态：有列车延误 5 分钟以上就算「延误」，分钟数取最大值。说明文字里写明「由本原型汇总」。
- **备选**：不显示线路状态，只列列车。
- **理由**：界面要的是线路级的信息。5 分钟这个阈值是本原型定的，不是运营商的标准，代码和文档里都写了。发车信息只有在数据给出站台号时才挂到番线上，否则不显示。

### H7. 适配器没有对真实响应验证过

- **决定**：照 ODPT 的 API 规格和目录页写，字段全部防御式读取，对不上的一律不猜。测试用的是自己构造的、形状符合规格的数据，并在测试名里写明不是录制的响应。
- **理由**：写的时候没有密钥。这是一个明确的未验证项，记在 REPORT 里。
